# Patterns Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a second kind of effect, the pattern: a colour per LED, built on one kind of device, played identically by every device of that kind in a group, saved in a file that already has room for frames and motion.

**Architecture:** The spine gains `pattern.rs` (the pattern document, its file, the fit rules' types) and one default method on `Effect`, `as_pattern`. A pattern is an effect id (`pattern:<name>`) that a group plays through the existing `Plays::Effect`, so scenes, favourites, the picker and `GET /effects` carry it without a new kind of `Plays`. In the engine, a group whose effect answers `as_pattern` skips the canvas: the fitted colours per light are computed once when the effect, the plan or the hardware changes, then copied each frame through the same group-brightness and global stages. The editor takeover is a third draft kind that lights the lights of the pattern's kind and dims the rest.

**Tech Stack:** Rust (canvas-proto, canvas-core, canvas-daemon), axum, serde, ts-rs; Next.js static export, React, vitest, CSS modules with the tokens in `app/web/src/styles/`.

**Spec:** `docs/superpowers/specs/2026-11-12-patterns-design.md`. Read it first. This plan argues from it and changes none of its decisions. Where the spec is silent the plan makes a call and marks it "Plan call"; the main agent confirms each before its task starts. The siblings are `docs/superpowers/specs/2026-11-12-scenes-design.md` (shipped on the Scenes branch) and `docs/superpowers/specs/2026-11-12-chain-setup-design.md` (0.15.0, issue #338, **not built yet**).

**Code base the line numbers come from:** `feat/scenes` at `df4cc41a`, the finished Scenes work. Citations read `path:line @scenes`. Every builder runs `git pull` on the integration branch before reading. Chain setup will move some of these lines; Task 0 re-checks the ones it can touch.

## Review Focus

Inputs the spec implies and that are most likely to bite. Each has a test in the task named.

1. **Chain setup is run again and a part of a split zone changes its LED count while a group plays a pattern on it.** The fit is worked out again, the part is flagged stretched, no frame of the old length is sent, no panic. (Task 3, `a_resized_light_is_refitted_without_a_stale_frame`)
2. **A pattern a group plays is gone or damaged** (deleted by hand in `patterns.json`, a frame with the wrong number of colours, unparseable JSON). Only that group is dark and says why; every other group runs; the daemon starts; good patterns in the same file still load. (Task 4, `a_damaged_patterns_file_keeps_the_good_patterns`; Task 6, `a_missing_pattern_darkens_only_its_group`)
3. **A one-LED device, and an all-off pattern.** A single LED takes the first colour that is not off and is flagged; an all-off pattern gives it off and the flag; an all-off pattern on a ring is black, not an error. (Task 2, `a_single_led_takes_the_first_colour_that_is_on`, `an_all_off_pattern_is_all_off`)
4. **The editor sends strokes faster than the daemon applies them, or the window closes mid-stroke.** An older stroke never replaces a newer one (`applied: false`), and the lease ends by itself and puts the active scene back. (Task 7, `an_older_stroke_never_replaces_a_newer_one`, `the_lease_ending_puts_the_scene_back`)
5. **A fan wired the other way (`reversed`) or built on a device whose own `reversed` differs from the target's.** The pattern is stored in position order (as the owner sees the device) and each target applies its own `reversed`, as a canvas effect does, so the marked LED lands on the same visible spot on every fan. (Task 3, `a_reversed_light_shows_the_pattern_the_other_way_round`)

- Produces:

```rust
/// The colours for one light, in position order (the order the owner sees the device in; the
/// engine applies the light's own `reversed` afterwards). `source` is the pattern's frame.
/// `source.len()` equals `built_on.led_count`. The result has `target_leds` entries.
pub fn fit_colors(source: &[Rgb8], built_on: &BuiltOn, target_leds: u32, target: Arrangement) -> Vec<Rgb8>;
```

Rules, pinned (spec "Fit"; the rounding rules are Plan calls):
- Exact: a copy.
- OneLed: the first colour of `source` that is not black, else black.
- Stretched on a ring: target LED j of m reads source index `round(j * n / m) % n`, ties up. LED 0 stays LED 0, a LED a quarter round stays a quarter round.
- Stretched on a strip, a single or a grid: j of m reads `round(j * (n - 1) / (m - 1))`, so the first LED reads the first and the last reads the last. A one-LED source (`n == 1`) fills every LED with its colour. **Plan call:** a grid with a different count is stretched by LED order like a strip. The spec says "position along the ... grid" and `built_on.grid` is in the file for a later two-dimensional version; a two-dimensional stretch needs the zone's cell map for both devices and is not in 0.16.0.
- OtherShape: the strip formula over LED order, whatever the arrangements. Equal counts copy.
